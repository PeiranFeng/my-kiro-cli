# 表达规约与描述代码行为

## 写作规约

### 只写看代码看不出的内容  {#only-non-obvious}

steering 与 skill 只记录"看代码看不出来但必须知道"的内容。禁止信息重复——同一事实只在一处出现，其他地方引用或省略，避免修改时不一致。信息来源优先级：仓库代码 > steering > skill。高优先级来源已有的信息，低优先级只记录引用位置，不重复内容。

### 只记录普适原则，不用具体例子  {#no-examples}

只记录普适原则，不用具体例子作补充说明。例子过短则不够精确，上下文切换后无法提供有效信息；例子过长则污染上下文。

### review 标记与 checklist  {#review-marker}

条目标题后带 `[review]` 标记，表示该原则是 code review 应覆盖的检查项。checklist 由 `user-review` skill 扫描所有 steering 文件中的 `[review]` 标记动态生成，不手工维护清单。

### 语言要求  {#language}

所有回复只能使用中文或英文，禁止其他语言。上传到 GitHub 的文字一律使用英文，包括 commit message、issue 描述、PR 标题和描述、PR comments。

### 需求文档用肯定式  {#affirmative-docs}

需求、计划、设计等面向尚未发生之工作的文档，直接肯定地陈述"要做什么"。否定式陈述（"不要这样做"）须有一个已存在的错误对象作靶子，只适用于对既有错误给出改正意见的场景（如 code review）。若判定某项需求不成立，直接删除该项，而非保留它再附一句否定说明。

## 描述代码行为

适用于主动解释、review 记录、skill 输出等一切需要描述代码做了什么的场景。

### 禁止裸名词  {#no-bare-names}

引用变量名、方法名、类名时，必须附有能让读者定位该名称的上下文；裸名称单独出现，读者无法判断它属于哪里、是什么。

### 解释的最小单元是类/模块  {#explain-from-class}

解释某个方法、代码段或变量前，先判断上下文中是否已介绍过它所在的类/模块。若未介绍，先说明该类/模块封装了什么数据、提供什么行为、对数据有什么约束，再说明具体方法/变量在其中的定位，然后进入解释。

### "是什么"与"为什么"分开  {#what-vs-why}

是什么 = 操作和结果；为什么 = 目的。二者不混。

### 每个描述词对应代码里具体一行  {#word-maps-to-code}

每个描述词必须对应代码里的具体一行，对应不上就是比喻，换掉。

### 外部工具默认未知  {#external-tools-unknown}

数学概念、PyTorch/Triton/CUDA 等框架知识不假定读者已知；已出现在 `deep-dive/base-line/` 的概念视为已知基线，其余一律解释或明确标注"假定读者已掌握"。

### 解释外部工具后更新 base-line  {#update-baseline}

用户明确表示不理解某个外部工具或数学概念，且该概念不在 `deep-dive/base-line/` 中时，解释后在对应文件（`math.md`、`pytorch.md`、`triton.md`、`cuda.md`）末尾追加该概念，格式包含接口签名（如适用）、定义说明、`Last mentioned` 日期。`base-line/` 只追加，不删改已有条目。

### 回复中的引用必须自明  {#self-contained-refs}

不使用需要读者查找外部来源才能理解的指针（裸锚点、缩写、代词等）。每个引用在当前句中给出足够上下文，使读者无需跳出当前回复即可理解。
