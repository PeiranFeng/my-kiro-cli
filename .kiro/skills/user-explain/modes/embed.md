# 模式：embed

用户要求让某个 skill 接入 user-explain 时，读取目标 skill，输出接入建议。只出建议，不修改目标 skill，用户另行要求时才修改。

## 流程

1. 读目标 skill 的全部文件，列出它的接口或步骤，标出哪些产出对话回复，哪些只写文件或执行操作。
2. 对每个产出对话回复的接口，按下面的建议清单逐条核对，选出适用的条目，写明具体落点：哪个文件、哪个步骤之后。
3. 用编号列表输出，每条包含：建议、落点、理由。

## 建议清单

1. 写成显式步骤，不写成引用。接口自己的步骤里要有"按 user-explain 写回复"一步，放在信息收集和分析完成之后，作为该接口的最后一步。写在文末的一句引用容易被遗漏。
2. 把验收写进该步骤：要求过 `user-explain/checklist.md` 全部项，再过接口自己的验收项，任何一项为否就改写。
3. 接口验收项只写该接口特有的检查，不重复 `checklist.md` 已有的内容，每项是"是/否"问题。
4. 指向场景：接口的输出落在 `scenarios/` 的哪个场景，就直接指向该场景文件，宿主自己的必答要素只补场景文件没有的项。
5. 宿主的固定格式只规定内容结构与字段，不规定措辞与详略。读者缺的前提、术语解释和详略判定留给 user-explain；固定格式里对读者可能陌生的字段，要留出"先说这项在说什么"的位置。
6. 按需引用文件：宿主的步骤里只引用用到的 `principles/`、`scenarios/` 文件和 `domain/INDEX.md`，不要求整体加载。
7. 不把 user-explain 的规则复制进宿主，宿主只引用路径，同一事实只在一处出现。
8. 只写文件或执行操作、不产生对话回复的接口不接入；写出的文件是给人读的文档时，只引用 `principles/writing.md` 与 `principles/wording.md`，不走 `checklist.md`。
9. 宿主有只读或简短的使用场景时，注明可与 `static`、`short` 组合；与 `static` 组合时，以 `static` 的禁令为准。
10. 宿主遇到背景知识缺口时，按 user-explain 的取材顺序：先读 `domain/`，没有再 web 搜索或用模型内部知识。宿主不自行写入 `domain/`。
11. 接入后做对照验证：同一个任务接入前后各跑一次，确认验收项能拦住之前的遗漏。一次样本不构成结论。
