# 新旧版本的对比：一致性与性能

一致性与性能是两个独立的目标，按需要分别做；`feature-lab` 与 `preprocess_evaluate` 的改动用同一套做法。

## 一致性

一致性要证明的是：在一份双方都能读的输入上，新旧两版的输出相同。输入不必是最新的数据，只要两边读的是同一份；差异只有在这个前提下才能归因于代码。

### 输入：快照及其复用

`preprocess_build.py` 的每次 build 都读一份上游快照，两版读同一份快照即满足前提。`verify` 复用已有的快照与 build，只在下面三个判断不成立时才多 build：

1. **快照适配版本**（输入兼容）：快照里该版本要读的每个 relation，列名与类型都和当前上游相同；运行时才发现列的上游（因子宽表、scoring 表）因此要求列集合完全相同。快照缺的 relation 从当前上游补进去：另一版本不读它，它的输出不受影响，所以补完仍可比。
2. **已有 build 代表对照版本**（对照输出兼容）：两者的 rev 之间，diff 没有碰到该层执行的代码——feature-lab 的 `models/preprocess`、`macros`、`dbt_project.yml`，preprocess_evaluate 打进 zip 的模块。dev 上无关的合并与上游数据的日常更新都不触发重 build。
3. **输出可比**（候选键兼容）：见下面的"比对"。

`verify` 按 A、B、C 的顺序选（细则见脚本头部），并在结果里写明选了哪条、为什么：A 复用一次代表对照版本的 build，只 build 新版本；B 复用一份双方都适配的快照，build 两次；C 新拍快照，build 两次。

仍然要 build 两次的情况：该快照上还没有对照版本的 build（一个 PR 的第一次验证）；对照版本有实质变化；对照版本所读 relation 的表结构变了，需要新快照；两版所读的输入根本不兼容——这时一致性无法证明，只能比性能，表结构不同时测性能用同量级的伪造数据（见下面的性能一节）。

两个仓库同时改时，一次对比分不清差异来自哪一边；要归因就分两次对比，每次只变一个仓库的 rev。

### 比对

1. 用 `scripts/compare_tables.py`（判定口径见脚本头部），逐表比较两次 build 都 clone 出的层内表；PR 范围外的表（如未改动的 index）用 `--exclude` 排除。
2. 连接键在任一边不唯一时报"粒度不同"并停止：重复键会让 join 产生交叉行，比出的差异没有意义。
3. 表结构不同时看新旧之间去掉了哪些列：
   - 去掉的都不是候选键：粒度不变，在共同键上比较其余列，结论可靠。
   - 去掉了候选键的一部分：粒度变了。新表更粗（按剩余键聚合）时，知道聚合方式就把旧表按同样方式聚合后再比；新表更细（数据量扩大）时，只有旧表每行能由新表若干行确定推出才能比，否则说明无法证明一致。
   - 改名的列表现为一删一增，先对齐列名；同名列的含义变了会报出差异，这是真实发现。
4. 容差：数值相对差 1e-9 以内视为相同。同一份输入上，浮点累加顺序会带来约 1e-15 的差异，SQL 中的浮点聚合（加权平均、偏度等）可到 1e-12。NULL/NaN 的位置与 ±Inf 不受此影响，必须完全一致。

## 性能

- 只看新版本代码的最近一次 build，旧版本非必要不重复 build。`build` 的 summary 给出整层耗时（第一个 model 开始到最后一个 model 结束）、每个 model 的总耗时减排队时间，以及最慢的几条查询的剖面（`profile.txt`）。
- 用 `scripts/query_profile.py` 读最慢的查询与 diff 涉及的查询，按 `sql/verify.md` 的四项检查官方列出的常见问题：join 膨胀、多余的去重、溢出、裁剪无效。
- diff 中新增或修改的算子，读代码判断时间与空间复杂度是否随窗口、分区大小、因子数异常增长（如每行重算整窗）；读代码有疑点时，在两种数据规模上各 build 一次核实增长率。
- 表结构不兼容、无法在真实输入上运行时，用伪造数据测速：伪造数据对齐决定耗时的量——分区数与每个分区的行数分布（timing 是每只股票的历史长度，cross-section 是每个 rule、每天的股票数）、因子数、NULL 密度、窗口参数。
- warehouse 与他人共用，同一份代码在不同负载下总耗时可相差近一倍；汇报时附上该次 build 用的 warehouse 与运行时间段。
- 线上参照：DEV 每天定时运行中各任务的起止时间可用 `scripts/dev_task.py status` 读出（`TASK_HISTORY`），作为新代码 build 耗时的对照背景，不替代新代码自己的 build。

## 汇报

依次写：两个版本的两个仓库 commit、`verify` 选的方案与理由、每张表的比对结论（粒度不同、主键集合差异、不一致的列）、失败的 dbt test、新版本的整层耗时与每个 model 的执行时间（附 warehouse 与运行时间段）、剖面与复杂度检查发现的问题。
