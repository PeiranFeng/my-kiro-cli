# project-model

把人的自然语言决策编译成可版本控制的项目模型。用户负责目标、关键取舍和验收语义；本 Skill 负责目录、节点、稳定 ID、交叉引用、场景覆盖和后续同步，不要求用户手写结构化 Markdown。

执行前声明“依据 project-model skill”。

## 适用边界

本 Skill 只维护目标仓库的 `docs/project-model/`。可以读取目标仓库的代码、测试和已有文档，不修改生产代码、自动化测试、Git 历史或远程资源。

代码是现状证据，已批准模型是预期行为。二者冲突时报告差异，不用代码现状覆盖已批准模型。

生成或修改模型前读取：

- `references/model-contract.md`：目录、元数据和完整性规则。
- `references/document-templates.md`：各类节点的 Markdown 骨架。

## 确定目标仓库

每次动作先确定一个或多个目标仓库根，并在整次动作中使用其规范化绝对路径：

1. 用户明确给出路径时，以该路径为目标；相对路径从当前工作目录解析。
2. 用户未给路径且当前目录属于 Git 仓库时，使用 `git rev-parse --show-toplevel` 的结果。
3. 当前目录不属于 Git 仓库且上下文不能唯一确定目标时，只询问目标路径。

不得用 Skill 所在目录、用户主目录、上一次处理的仓库或相邻仓库作为默认目标。不得因为另一个仓库存在 `docs/project-model/` 就读取或修改它。

每个仓库独立保存自己的项目内容：

```text
<repo-root>/docs/project-model/
```

Skill 本身只保存通用流程、契约、模板和脚本，不保存任何目标项目的名称、需求、架构、用例、状态或路径。

一次请求明确涉及多个仓库时，先列出并确认仓库根集合，再按仓库分别读取和写入各自的 `docs/project-model/`。一个仓库的模型节点、校验报告和生成目录不能写进另一个仓库。用户没有指定统一协调仓库时，不创建中央模型，也不把其中一个仓库当作其他仓库的事实源。

## 安装范围

个人在多个仓库复用时，可把 `project-model` 和 `project-maintainer` 安装到全局 Skills 目录；团队共享时，可把同版本 Skills 放入各仓库的 workspace Skills 目录。无论 Skill 安装在全局、目标仓库还是临时控制仓库，项目内容始终只写入目标仓库的 `docs/project-model/`。

从临时控制仓库运行时必须显式给出目标仓库。Skill 脚本的位置从已加载 Skill 自身解析，`--project-root` 始终传目标仓库根；不能以脚本所在仓库代替目标仓库。

## 确定动作

按用户意图选择动作：

- `bootstrap`：从自然语言、已有文档和可选代码生成初始双树。
- `change`：把增量需求传播到受影响的架构节点、接口用例和联合用例。
- `reconcile`：从已有代码和测试补充现状，生成差异报告，不改写已批准语义。
- `approve`：用户明确批准后，将确认范围内的草稿节点改为已批准。
- `validate`：只运行确定性校验并解释问题。

用户没有指定动作时：模型不存在则使用 `bootstrap`；模型存在且用户描述新行为则使用 `change`；用户要求代码与文档对齐则使用 `reconcile`；用户表示批准则使用 `approve`；用户只问完整性则使用 `validate`。

## Step 1 — 收集证据

1. 读取用户的自然语言描述。
2. 检查 `docs/project-model/`；存在时先读入口和受影响分支。
3. 只读取判断边界和现状所需的代码、测试与项目说明。
4. 检查目标仓库未提交改动，不覆盖与本任务无关的用户修改。

内部区分四类信息：用户明确要求、代码现状、推荐设计、待确认决策。不得把代码现状或推荐设计表述成用户要求。

## Step 2 — 只询问决定性问题

先作出专业判断并给出推荐结论。只有不同答案会改变系统边界、公开契约、数据所有权、一致性、安全、迁移或验收语义，且无法从上下文可靠推断时，才询问该具体前提。

低风险实现细节由 Agent 决定。多个相关问题合并成简短决策摘要；用户确认前可以形成 `draft` 提案，不能形成 `approved` 结论。

## Step 3 — 生成或演进双树

### bootstrap

1. 按系统、领域、模块、组件或类、公开接口和约束分解架构。
2. 在 `architecture/` 中生成需求与架构节点。
3. 在 `use-cases/` 中镜像公开接口路径，生成正常、异常、边界、安全和状态转换场景。
4. 在 `use-cases/journeys/` 中生成跨接口、跨模块或跨仓库的联合流程。
5. 生成 `docs/project-model/README.md`，说明模型入口、状态和自然语言维护方式。
6. 未获用户明确批准的节点使用 `status: draft`。

### change

1. 以稳定 ID 查找受影响节点，不按标题猜测身份。
2. 计算直接接口、依赖节点、接口用例和联合用例的影响范围。
3. 保留未受影响内容和节点 ID；移动文件不更换 ID。
4. 同一次修改同步更新架构树和用例树。
5. 行为被替代且仍需追溯时将旧节点标为 `deprecated`；无引用的错误草稿可以删除。
6. 输出语义差异，不要求用户逐文件核对格式变化。

### reconcile

1. 从公开符号、入口、配置和测试识别实际结构。
2. 为文档缺失但代码已存在的公开行为生成 `origin: reconciled` 的草稿节点。
3. 将模型与代码的缺失、额外和疑似不一致写入 `docs/project-model/generated/reconcile-report.md`。
4. 不根据现有测试自动改变已批准用例的期望。

### approve

1. 明确批准范围；用户说“全部批准”才处理全部草稿。
2. 先执行校验。存在错误或未决语义时不批准，并指出最小阻塞项。
3. 只更新状态和必要的设计依据，不重写无关正文。
4. 批准后再次执行校验。

## Step 4 — 控制文档粒度

目录表达所有权和层级，Markdown 表达契约和行为。公开接口在两棵树中使用同一相对路径。一个接口的多个场景写在一个用例文件中；联合流程写入 `use-cases/journeys/`。

项目模型治理公开、稳定和跨边界的行为。私有辅助类与私有方法默认由代码表达。用户要求完整类清单时，将易变私有实现清单生成到 `generated/`，不把它变成人工审批负担。

## Step 5 — 运行确定性校验

每次修改后运行 `scripts/validate_model.py`。选择本机已有的 `python3`、`python` 或 Windows `py -3`，不安装依赖。

```text
<python> <本-Skill目录>/scripts/validate_model.py --project-root <目标仓库> --report docs/project-model/generated/validation.json
```

校验失败时修正文档结构和引用。有效需求、用例期望和节点状态不能为了通过校验而被删除、弱化或废弃。

## Step 6 — 汇报

汇报以下内容：

- 动作和目标仓库。
- 新增、修改、移动和废弃的语义节点。
- 推荐设计及其依据。
- 仍需用户决定的具体问题。
- 实际校验命令、退出码、错误数和警告数。
- 下一步是批准、继续补充，还是交给 `project-maintainer review|implement|maintain`。

文件清单不能代替语义摘要；未经实际校验不能声称模型完整。

## 与 project-maintainer 交接

进入代码维护前，本 Skill 提供目标仓库、已批准范围的 architecture/use-case ID、最新模型校验报告、`modelFingerprint` 和 `modelSemanticFingerprint`。范围内存在 `draft`、校验错误或未决语义时不交接实施。

`project-maintainer` 将批准后的正文和语义关系视为只读。它可以在真实文件与符号已经核查后机械更新架构节点的 `implementation` 和用例节点的 `automation`；这些映射变化不构成新的架构决策。

`project-maintainer` 发现需求、接口、依赖或用例期望需要变化时，必须产生 specification blocker 并回到本 Skill 的 `change` 动作。用户用自然语言作出决定后，本 Skill 同步双树、重新校验并生成新指纹，再由 `project-maintainer resume` 重新计算未完成范围。
