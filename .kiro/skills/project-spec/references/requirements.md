# requirements

`requirements <自然语言>` 把用户的描述变成需求树中的 draft 需求。写文档之前先审核描述：对不合理的需求说不，是本命令的职责。

## 准入审核

依次对描述做四项审核，结论附文件、命令输出等证据。任一项未通过，本次的产出是给用户的反馈，不是需求文档。

1. 现状：阅读目标仓库已有的需求、架构和代码，判断需求是否已被当前系统满足。已满足且不是对现有架构的升级时，指出满足它的文档或代码位置，请用户确认是否仍要继续。
2. 可行性：评估是否经过任何技术路径都很难实现。很难时说明困难所在和代价，请用户决定是否调整需求。
3. 能力：评估本 skill 与当前 Agent 能否胜任。无法胜任时说明困难，以及本 skill 在这类需求上的局限。
4. 清晰度：参与者、触发条件、可观察结果、边界任一项不明时，向用户提问；一轮不够就继续提问，直到用户想清楚。每轮只问影响语义的问题。

四项全部通过后才写需求文档。

## 小样

用户尚未想好、并明确要求先生成一版看看时，才生成小样。Agent 可以提示用户有这个选项，由用户决定。

- 小样是一份 draft 需求，审核中未解决的问题全部写进它的 `## 待确认`，只生成一版。
- `approve` 不批准含 `## 待确认` 的文档，所以小样在问题解决前不会进入下游。
- 用户据小样想清楚后，需求重新走准入审核，再修改该文档并清空 `## 待确认`。

## 写作

1. 把描述拆成模块功能点，跨模块约束写成项目级需求，遵守 stage 含 `requirement` 的全部原则。
2. 修改已有需求时把它改回 `draft`；不再成立的需求直接删除，并删除只为它存在的引用。
3. 运行校验，通过后自动 review。
