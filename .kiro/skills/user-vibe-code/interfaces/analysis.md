# 接口：analysis

分析一个实际发现的 AI 开发问题，从中归纳出适配于自定义开发的原则，追加到 `domain/ai-dev-problems.md`。案例本身不入库，只入归纳后的原则。用户指出某个问题时直接执行；develop 或 review 中发现新形态的问题时，在该接口完成后转入本接口。

## 触发

- 用户指出 AI 写的代码有问题，或指出某个结论、建议不成立。
- review 接口发现了问题，且该问题的形态不在 `principles/ai-failure-patterns.md` 与 `domain/ai-dev-problems.md` 已有内容里。
- 用户明确要求分析或记录某个问题。

## 步骤

1. 还原现象：AI 做了什么，产出了什么，哪里不对。只写事实，来源是用户的描述或读到的代码。
2. 定性：这个问题落在哪类，防御、范围与熵、契约、失败方式、测试，或不属于现有任何一类。
3. 找成因：AI 为什么会这样做。成因要落在可观察的行为上，如没有核实前提就下结论、把可能性当成可达路径、为让代码不报错而兜底、沿用训练中见过的通用写法而非仓库写法。无法判断成因时写"未确定"，不编造。
4. 对照原则与已有形态：先查 `principles/ai-failure-patterns.md` 是否已有同类形态；现有的 `principles/` 是否已覆盖。已覆盖，说明为何仍然发生，是原则不够具体、没有被读到，还是被其他规则压过；未覆盖，写出缺哪一条。
5. 提炼检出方法：下次 review 时用什么问题、什么搜索或什么检查可以发现它。
6. 归纳原则：去掉仓库、文件、函数、表名、具体数值，写成换一个仓库仍成立的原则（`10-communication.md#no-examples`）。
7. 准入与追加：过下面的三关后，追加到 `domain/ai-dev-problems.md`。
8. 汇报：回复列出追加的条目、被拒绝的条目与未通过的关，以及建议修改的 `principles/` 条目。

## 准入

一条内容须同时通过三关才追加：

1. 通用性：不依赖具体仓库、commit、文件、函数名、表结构或数据快照。
2. 查重：已有条目覆盖同一现象与成因的，不重复追加；有新的触发条件或检出方法时，在原条目上补充并记录补充日期。
3. 已验证：条目带验证记录，两种之一：用户确认（用户明确说这个问题成立）、实验（环境、命令、结果）。缺验证记录时不追加，只说明缺什么。文献与公开实践不进 domain，整理进 `principles/` 并在 `principles/sources.md` 记出处。

## 从 domain 到 principles

同类条目积累到可以归纳时，提出将其整理进 `principles/` 的建议：说明涉及哪些条目、归纳出的规则、应落在哪个文件。

## 对 principles 的修改

分析得出的结论如果要求新增或修改 `principles/` 的条目，只在回复里提出建议，由用户确认后再改。

## 条目格式

见 `domain/ai-dev-problems.md` 的头部。

## 验收

1. 条目是否去除了仓库、文件、函数、数值等具体内容？
2. 条目是否带验证记录，并已查重？
3. 对 `principles/` 的修改，是否只提了建议、未擅自改动？
