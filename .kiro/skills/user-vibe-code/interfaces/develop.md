# 接口：develop

在约束下写或改代码。新增功能、修改功能、处理外部输入、修复缺陷共用这套步骤，差异见末尾。

## 步骤

1. 定范围：复述用户已确认的方案，只实现它，并把任务转成可验证的完成标准（`principles/scope.md`）。需求有多种解读时列出并请用户选。
2. 看周边：读被改动处的上下游与同类代码，记下既有的命名、工具函数、错误处理与测试写法（`principles/repo-conventions.md`）。
3. 查前提：对代码要消费的每份数据，按 `interfaces/premise.md` 的方法确认其契约及强度；改动很小、不涉及新的数据消费时可略。
4. 写最小实现：沿用周边的写法与已有的工具函数，不新增并行机制。
5. 过三问：对每一处想加的校验、try/except、默认值、兜底、可选参数，按 `principles/defensive.md` 决定去留；形态与失败方式按 `principles/failure.md`。
6. 写测试：按 `interfaces/testcase.md` 为保留的 guard 与新行为写用例。
7. 写后自查：把自己的改动当作 `interfaces/review.md` 的审查对象过一遍，答不上的 guard 和不能追溯到需求的新增删除。
8. 回复：呈现下方"回复内容"，过 `checklist.md` 的 develop 与共用部分。

## 轻量路径

单点修改、不新增数据消费、不新增 guard 时，只执行步骤 1、2、4 和写后自查中的三问，回复一句话说明沿用了哪处写法。

## 回复内容

- 代码依赖的数据契约、依据与强度，每份一句。
- 保留的每个 guard 及其触发路径，每个一句。
- 沿用的既有写法所在的位置。
- 契约无法查证而需要用户确认的点，只问那一项。

## 场景差异

- 处理外部输入：这是信任边界，校验集中在入口处一次完成，通过后内部按契约使用；校验失败按 `principles/failure.md` 报出具体违反项。
- 修复缺陷：先写出能复现缺陷的用例并确认失败；定位根因所在的一方（生产方违反契约，或消费方误解契约），在根因处修；不在下游加兜底来掩盖症状。
- 清理、去重、重构：保持行为不变，没有测试作对照时只报告；规则见 `principles/repo-conventions.md`。
- 修改既有功能：在被改动的函数内保持结构完整，不为了让改动最小而叠加补丁；范围之外的重构先问用户。

## 验收

- 没有无法追溯到需求或触发路径的分支、参数、配置。
- 没有吞异常，没有未经用户确认的默认值。
- 没有与既有写法并存的第二套机制。
