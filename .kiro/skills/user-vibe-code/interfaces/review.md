# 接口：review

审查一份 AI 开发的改动，是否违反本 skill 的原则。只在回复里呈现，不写文件，不改代码，不发评论。通用的代码设计审查归 `user-review`，不在此做。

## 审查对象

本地未提交改动、某个提交范围或某个分支与基线的差异。执行 git 命令前先明确目标仓库（`40-git-safety.md#identify-repo`）。

## 步骤

1. 取 diff，列出改动的文件与函数。
2. 读每处改动的周边代码与被消费数据的生产方，建立判断所需的证据。读取范围限于 diff 涉及的文件与必要的类型实现。
3. 读 `principles/ai-failure-patterns.md` 与 `domain/ai-dev-problems.md` 的已有条目作为检查线索，再按下面四类检查逐处过一遍。
4. 逐条给出发现，写回复并过验收。发现了现有形态目录与原则库里都没有的问题时，转 `interfaces/analysis.md`。

## 四类检查

### 防御

对新增的校验、try/except、默认值、兜底返回、空值处理、类型转换、可选参数、重复的上游检查，逐个按 `principles/defensive.md` 的三问判断：触发路径是否可达、是否已被上游保证、不加的后果是什么。同时按 `principles/failure.md` 检查断言与错误处理是否混用（用断言校验外部输入，或用错误处理恢复内部缺陷）、是否吞异常、是否有未经确认的默认值、继续运行的失败是否可见。

### 范围与熵

- 新增的分支、参数、配置、文件、抽象，是否都能追溯到已确认的需求。
- 是否有现成的工具函数或写法被另写了一份（用搜索确认时，空结果须换一种方法二次确认，`20-engineering.md#empty-search-not-absence`）。
- 命名、目录位置、错误处理、测试写法，是否与周边既有写法一致。
- 是否为未来需求预留了抽象、开关或扩展点。
- 是否新增了未经确认的第三方依赖。

### 契约

- 代码依赖的数据前提是否有依据，落点是验证、假设还是注释。
- 前提与生产方的实际承诺是否一致。

### 测试

- 期望值是否独立于被测实现。
- 每条入口校验与 raise 是否有直接触发它的用例。
- 是否为让测试通过而改了期望值、放宽了断言，或在实现里为测试输入写了特判。
- 是否为契约外取值写了防御性用例，是否测的是实现细节而非行为，用例里是否带逻辑。

## 豁免

下列情形即使形态相同也不算问题，评估时标"有理由，保留"：信任边界处的校验；有书面理由且有回退用例的兜底；仓库既有架构与约定要求的写法；用户声明为探索性的代码，其中的临时重复与硬编码在进入核心包、共享模块、稳定接口或合入路径时失效。

## 每条发现的写法

- 位置：文件与行号。
- 违反的原则：指向 `principles/` 中的条目。
- 依据：读过的代码或统计，附位置。查不到依据时，结论写"需确认"，并说明缺什么，不写"可能有问题"。
- 处理建议：删除、保留（并写明触发路径）、改写，或请用户确认。

无发现的类别明写"无"。末尾给出总体结论：哪些必须在合入前处理，哪些可以保留，各自的依据。

## 验收

1. 每条发现是否都有读过的代码作依据，且写明位置？
2. 每个"删除"建议，是否确认了该 guard 在真实数据下无可达触发路径、且无已知的静默后果？
3. 是否没有混入通用的命名、注释、OOP 审查？
4. 是否没有改代码、没有发评论？
