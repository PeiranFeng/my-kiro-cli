# 接口：code-review

审查一份 AI 开发的代码改动，是否违反本 skill 的原则。只在回复里呈现，不写文件，不改代码，不发评论。通用的代码设计审查归 `user-review`，不在此做。

## 审查对象

本地未提交改动、某个提交范围或某个分支与基线的差异。执行 git 命令前先明确目标仓库（`40-git-safety.md#identify-repo`）。

## 步骤

1. 取 diff，按 `objects/代码.md` 列出各项并读周边代码与被消费数据的生产方。
2. 以 `principles/` 各节的"常见形态"与 `domain/ai-dev-problems.md` 的已有条目为线索，按 `objects/代码.md` 指定的 `checklist.md` 部分逐项打分（测试代码按 `objects/测试.md`），答"否"的写成发现。
3. 写回复，交出前按 `checklist.md` 的五打分。发现了 `principles/` 与原则库里都没有的问题时，转 `interfaces/analysis.md`。

## 豁免

下列情形即使形态相同也不算问题，标"有理由，保留"：信任边界处的校验；有书面理由且有回退用例的兜底；仓库既有架构与约定要求的写法；用户声明为探索性的代码，其中的临时重复与硬编码在进入核心包、共享模块、稳定接口或合入路径时失效。plan-review 接口共用本节。

## 回复内容

按问题组织，不按检查清单的类别或条目组织，也不逐项列出"是/否"。每个问题一条，按严重程度排列，含：位置、问题是什么、依据、处理建议（删除、保留并写明触发路径、改写，或请用户确认），并在该问题上标出它违反的原则，写原则的名称与出处（取 `checklist.md` 对应项末尾的"原则"），如"违反：框架取舍（`repo-conventions.md`）"。一个问题违反多条原则时都标出。没有问题时写一句话说明。末尾给出总体结论：哪些必须在合入前处理，哪些可以保留，各自的依据。
