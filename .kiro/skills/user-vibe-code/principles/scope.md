# 范围与最小实现

## 每一行代码对应一条已确认的需求

只实现用户确认过的方案（`00-collaboration.md#primary-goal-first`）。新增的分支、参数、配置项、兜底，每一个都要能追溯到一条已确认的需求，或一条在真实调用下可达的触发路径；追溯不到的不写。途中发现的范围外问题不处理（`00-collaboration.md#stay-on-task`）。

## 每一行改动可追溯

改动的每一行都要能追溯到用户的请求。自己的改动造成的孤儿（不再被引用的 import、变量、函数）一并清理；改动之前就存在的无用代码不动（`00-collaboration.md#stay-on-task`）。依据见 `sources.md`。

## 存在多种解读时列出来

需求有多种合理解读时，不默默选一种实现，把解读列出并请用户选；有更简单的做法时直接说出来。

## 简单优先

清晰优于技巧，简单优于完备，只有证明别无他法才写大程序。一个函数只做一件事，部件之间用清晰的接口相连，出问题时影响面局限在局部。依据见 `sources.md` 的 Art of Unix 条目。

## 命名与注释承担说明

- 名字声称的语义须与实际行为一致（`20-engineering.md#name-matches-behavior`）。
- 默认不写注释；只在代码无法表达的约束、不变量、规避手段处写一句话，解释为什么（`20-engineering.md#one-line-comments`）。
- 数据契约属于这类约束，写在消费数据的边界处。

## 特殊语义用独立字段

不把哨兵值混进正常取值区间的输出里表示特殊含义，用独立字段表达（`20-engineering.md#no-magic-values`）。默认值、空值、零值与"无数据"的含义不同，混用会让使用方无法区分。
