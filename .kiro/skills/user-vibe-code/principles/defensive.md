# 防御性代码的去留

## 为什么要设限

每个 guard 都带来一个分支，按 `20-engineering.md#coverage-standard`，每个 `if` 的两侧、每条 `raise` 都要有对应用例；处理异常的代码本来就比处理正常情形的代码难写、难测，处理点越多，系统越复杂（依据见 `sources.md` 的 APOSD 条目）。模型倾向于交出"能跑、不报错"的代码，所以会自发多加 guard，这要靠流程压住。

## 两类位置，两套判断

### 信任边界

外部输入、文件、网络、用户配置、跨团队接口所在的位置是信任边界。边界处的校验不适用下面的三问：外部数据的触发路径本来就写不出来，这里只问一件事，这个位置是否真的承接了不受自己控制的数据。是，就在入口处一次校验完，检查类型、长度、范围与可空性，通过之后边界以内的代码互相信任（依据见 `sources.md` 的 Code Complete 条目）。边界以内用 assert 或类型声明契约，不在每一层重复校验。

对不受自己控制的输入，严格拒绝比宽容接受更利于长期维护（依据见 RFC 9413 条目）。

### 边界以内

边界以内的每一处 guard（校验、try/except、默认值、兜底分支、类型转换、空值处理）依次回答（这三问是综合：来自对一次 AI review 误判的分析与上述文献的结合，待验证）：

1. 触发路径：能否写出一条在真实数据和真实调用方下可达的触发路径？写不出，不加。依据只能是读过的生产方代码、真实数据统计或用户的说明，"理论上可能"不算。
2. 已有保障：生产方、类型系统、框架或调用方是否已经保证了这一点（`principles/data-contract.md` 的查证顺序）？已保证，不重复。
3. 不加的后果：触发后若只是立即报出清晰的错误，崩溃本身就是 guard，不再额外加；若会得到静默的错误结果、损坏数据或安全问题，才值得加。

三问全部通过的 guard 保留，并在回复里写出它的触发路径。

## 形态偏好

同一个风险有几种处理形态时，按下列顺序选靠前的（形态来自文献，排序是综合，待验证）：

1. 改变语义，使该错误不存在：让操作在"目标已满足"时直接成功，让正常路径自动覆盖特殊情形，用类型和构造约束使坏状态无法表达。限度是，调用方需要知道的错误不能因此被隐藏。
2. 在低层处理，让上层不必知道；或把多处同类异常聚合到一处处理。
3. 在边界处 assert 或 raise，报出具体的违反项；程序遇到无法处理的错误时直接终止（`principles/failure.md`）。
4. 记录告警并继续，仅用于用户确认过可以继续的情形。
5. 兜底默认值。默认值意味着在出错时继续并给出一个猜测，是产品决策，须由用户确认，模型不自行决定。

依据见 `sources.md` 的 APOSD 条目与 `sources.md` 的 Effective C++ 条目。

## 模型常见的过度防御

写后自查和 review 时重点查这些形态：吞异常的 try/except、过宽的 except、出错时返回"安全值"、对已保证非空的值再做空值判断、对已约束类型的值再做类型转换、为未出现的调用方预留的可选参数与开关、与上游重复的校验、只为让测试通过而加的兜底、迁就测试输入的特判（见 `principles/testing.md` 的"不迁就测试"）。
