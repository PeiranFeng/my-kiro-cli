# 失败方式

## 失败要早、要响

发现"不可能发生的事发生了"，程序已不再可信，此后的行为都可疑，应尽早、明确地失败。继续运行并给出猜测，会把错误推迟到更远处，那时已无法定位。依据见 `sources.md` 的 Pragmatic Programmer 与 Art of Unix 条目。

## 未实现时显式失败

做不到的功能，显式抛出未实现的错误并说明缺什么，不返回硬编码的成功值、占位数据或空默认值；也不通过禁用、跳过或改写测试来显示完成。

## 断言与错误处理分工

- 断言表达"程序自身的缺陷不应发生"：内部不变量、已由上游保证的前提、"不可能"的分支。断言失败说明代码有缺陷，修代码，不在运行时恢复。
- 错误处理应对"预期会发生的坏情形"：外部输入、文件、网络、用户配置。按下面的策略报出或恢复。
- 两者不混用：不用断言校验外部输入（断言可能被关闭），不用错误处理去恢复内部缺陷。

依据见 `sources.md` 的 Code Complete 条目；"断言可能被关闭"随语言与运行方式而异，未核实。

## 处理策略在全仓库一致

发现坏数据之后怎么处理，是在健壮（出问题仍能运行）与正确（不返回不准确的结果）之间的取舍：立即报错停止、返回中性值、替换为其他值。选定的策略要清晰，并与仓库既有的错误处理一致（`principles/repo-conventions.md`）。依据见 Code Complete 条目。

## 出错信息写清四件事

出了什么错、在哪里、涉及哪个值、违反了哪条契约。契约违反时的信息直接引用契约内容。

## 只在能处理时才捕获

- 能真正处理（重试、回退到用户确认过的备选、清理资源）才 catch，只记录日志再原样抛出的捕获删掉，它让调用方与被调方的异常列表耦合，被调方新增异常时代码会悄悄过时。
- 捕获的范围限定在会出错的那几行，捕获的类型限定在预期的那几种。
- 必须捕获并继续时，继续的事实要可见：记录告警，输出里带可区分的标记，不让下游把"失败后的猜测"当成正常结果。

## 需要释放资源时

崩溃前要释放资源、写日志、收尾事务的环境，崩溃的原则不变，只在退出前做必要的清理。

## 正常时保持安静

程序没有意外要报告时不输出。日志只记录值得人工注意的事，满屏的正常日志会淹没真正的异常。
