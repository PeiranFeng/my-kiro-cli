# 测试用例设计

## 测试把契约变成可执行的检查

用例围绕两样东西设计：函数对外承诺的行为，以及它依赖的数据契约。契约外的取值不为它写"防御性用例"；入口处有 assert 或 raise 的，每一条配一个直接触发它的用例（`20-engineering.md#coverage-standard`）。

## 测行为，不测方法与实现

- 一个用例对应一个行为：在某个状态下对一组输入做出的某个保证，可用"给定、当、则"表述。方法与行为是多对多的关系，一个方法常含多个行为，按方法写一个大用例会随方法变复杂而越来越难读。
- 通过公开接口测试，断言结果状态，不断言内部交互与调用顺序，使用例在重构后不必改动。
- 用例名称说明所测的行为。
- 用例里不放逻辑分支和循环；需要循环判断时抽成只断言一个概念的小函数。
- 用例自成一体：读者无需跳到别处就能看懂输入和期望值的来源，又不夹杂无关的构造细节。

依据见 `sources.md` 的 Software Engineering at Google 条目。

## 选用例的方法

- 等价类划分：把输入按"预期得到同类结果"分成若干类，每类取一个代表。同类的第二个用例通常不带来新信息。
- 边界值：缺陷集中在取值区间的边缘，对每个边界取边界上、边界内一侧、边界外一侧。
- 决策表：多个条件组合决定结果时，列出条件组合与期望结果，防止漏组合。
- 状态转换：行为取决于历史时，列出状态与转移，每条转移一个用例。

## 覆盖标准

按被测方法的复杂度选标准，规则见 `20-engineering.md#coverage-standard`：逻辑复杂的方法满足分支覆盖，数值精度或安全性要求高的方法满足 MC/DC。涉及 tensor 计算的测试必须在 GPU 上执行（`30-domain-gpu.md#test-on-gpu`）。

## 期望值有独立来源

期望值的计算路径不得与被测实现走同一段代码，否则测试只是把实现和自己比较，永远通过。独立来源包括（本节为综合，来自一次测试只与实现自比的案例，待验证）：手算结果、更朴素的参考实现、公开的已知答案、满足的数学性质（上界、对称、守恒）。重写或优化一段实现时，把旧实现留作对照。

## 避免无效的测试

- 不写只断言 mock 自身的用例：所有协作者都被替换，测试因真实原因而失败的可能为零。
- 不用字面量或恒真的断言充数，不把同一场景换个名字重复测试。
- 用例要真正覆盖所声称的行为：通过的测试若测错了对象，比没有测试更危险。

依据见 `sources.md`。

## 不迁就测试

- 测试失败时，先判断是实现错了还是期望值错了，依据是需求与契约；不为让测试通过而改期望值、放宽断言、删除用例。
- 不在实现里为测试输入写特判，不加只在测试路径上生效的分支或兜底。
- 测试里的失败信息要指明哪个行为被破坏，让诊断不靠猜。

此条来自对 AI 编程常见倾向的经验判断，无文献依据，待验证。

## 用例的数量随 guard 数量

删除一个 guard 时，同时删除只为它存在的用例；新增 guard 须同时说明对应用例。保留 guard 却没有用例的，是未被验证的代码。

## 修缺陷先写复现

修缺陷前先写一个能复现它的用例并确认失败，再修，再确认通过。该用例留在测试集里，防止回退。
