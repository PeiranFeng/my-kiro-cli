# 与仓库既有写法保持一致

## 入乡随俗

写代码前先读周边：同文件、同目录、同类功能的代码怎么命名、怎么组织、怎么处理错误、怎么写测试，新代码照做。看到像约定的东西就遵守；认为某个约定不好时，告诉用户由其决定，不在新代码里悄悄另立一套。要换约定就换到底，不让新旧并存。依据见 `sources.md` 的 APOSD 与 Google 风格指南条目。

## 先找现成的再写

写新的工具函数、常量、配置读取、校验之前，先在仓库里找有没有现成的。搜索无结果时换一种方法二次确认再下结论（`20-engineering.md#empty-search-not-absence`）。已有实现能满足需求时直接用，不另写第二份。

## 不为未来预留

为尚未出现的需求而加的抽象、参数、开关、扩展点，一律视为有罪，除非用户已确认该需求。它们有构建成本、延迟其他功能的成本，以及让之后每次修改都更复杂的持有成本；而且预设的需求有很大概率不会按预想出现。这条只针对为未来功能增加的复杂度，不禁止为让代码更易修改而做的重构，也不禁止测试。依据见 `sources.md` 的 Yagni 条目。

## 抽象的准入

新增的抽象（基类、接口、工厂、注册表、策略、插件点、共用工具）须同时满足：现在已有两处以上真实的使用方；这些使用方在逻辑变化时需要同步修改；能用不含"和""或"的名字说清它做什么。只有一个实现、一个调用点的抽象，内联。依据见 `sources.md`。

## 并行机制就是熵

同一件事在仓库里出现第二种做法，读者就要多学一种，修改时要同步多处。新增的文件、模块、基类、装饰器、配置项，每个都要能说明为什么现有机制满足不了。项目约定的配置体系、目录与运行位置遵循 `50-project-facts.md`，不在此重复。

## 清理与重构保持行为不变

清理、去重、重构类的改动保持行为不变，包括错误类型与时序；没有测试作对照时，只报告不修改。发现的潜在缺陷只报告，不顺手"改进"；每次改动只做一类事，使它可单独审阅与回退。

## 不新增依赖

新增第三方依赖要有用户确认的需求。标准库和仓库已有的依赖能满足时直接用；确需新增时，说明它解决什么、现有依赖为何不够，并沿用仓库管理依赖的方式。此条为经验判断，无文献依据，待验证。

## 改动处的结构

修改既有代码时，改完的结构应像一开始就这样设计的，不靠叠加补丁让改动最小；这只适用于被改动的函数和类。范围之外的重构先问用户（`00-collaboration.md#stay-on-task`）。
