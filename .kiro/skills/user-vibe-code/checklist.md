# 验收清单

每项是"是/否"问题，任何一项为否就回到所选接口的相应步骤修改。所选接口文件另有验收项，一并执行。

## 共用

1. 每个新增的分支、参数、配置，是否都能对应到已确认的需求或一条可达的触发路径？
2. 是否没有处理范围外的问题？
3. 每个判断是否有读过的代码、统计或用户说明作依据，无依据的是否标了"需确认"？
4. 改动的每一行是否可追溯到请求，自己造成的孤儿是否已清理，既有的无用代码是否未动？

## 仓库一致性

5. 命名、位置、错误处理、测试写法是否沿用了周边既有写法？
6. 是否没有新增与既有机制并存的第二套做法？
7. 需要的工具函数，是否先找过现成的并二次确认了搜索结果？
8. 新增的抽象是否已有两处以上真实使用方？是否没有为未确认的未来需求预留参数、开关，也没有新增未经确认的依赖？

## 契约

9. 代码消费的每份数据，是否都查过生产方的承诺，并标了强度？
10. 强度为声明、快照、推断的契约，是否在入口处验证？
11. 调用的每个外部接口，是否在实际安装的版本里核实过？
12. 无法查证的契约，是否已向用户确认，并只问了那一项？

## 防御与失败

13. 信任边界处是否一次校验完，边界以内是否没有重复校验？
14. 边界以内的每个 guard，是否都写出了在真实数据下可达的触发路径？
15. 默认值与兜底，是否都经过用户确认？
16. 做不到的功能是否显式失败，而不是返回占位成功值？
17. 出错信息是否含出了什么错、在哪里、涉及哪个值、违反哪条契约？
18. 断言是否只用于内部缺陷，外部输入是否由错误处理而非断言校验？
19. 每个 try/except 是否都真的处理了异常，并限定了范围与类型？
20. 继续运行的失败，是否带有可见标记？

## 测试

21. 用例是否没有只断言 mock、字面量或重复场景？
22. 用例是否由等价类、边界值、决策表、状态转换推出，并对应一个行为？
23. 每条 raise 与每个入口校验，是否有一个直接触发它的用例？
24. 期望值是否来自独立于被测实现的来源？
25. 用例内是否没有逻辑，是否通过公开接口断言结果？
26. 测试失败时，是否先判断了是实现还是期望值有错，没有为通过而改期望值或加特判？
27. 清理、去重、重构类改动是否保持了行为不变？
28. 修缺陷时，是否先有失败的复现用例？

## analysis

29. 条目是否去除了仓库、文件、函数、数值等具体内容？
30. 条目是否带验证记录，并已查重？
31. 对 `principles/` 的修改，是否只提了建议、未擅自改动？
