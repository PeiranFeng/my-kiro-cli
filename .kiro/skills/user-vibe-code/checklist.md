# 交出前自查清单

本 skill 每种产物交出前逐项打分。每项是"是/否"问题，只看能否在产物、方案原文或读过的代码中指出对应的内容，不凭印象作答；指不出的答"否"。任何一项为"否"，回到所在接口的相应步骤修改。每项末尾的"原则"是它的出处，code-review 与 plan-review 标注违反的原则时取这里。

| 产物 | 打分的部分 |
|---|---|
| plan-review 检查的方案 | 一、二，方案含测试计划时加四 |
| develop 交出的代码 | 一、三、四 |
| code-review 检查的代码 | 一、三，改动含测试时加四 |
| testcase 交出的测试 | 四 |
| plan-review、code-review、premise 的回复 | 五 |
| analysis 追加的原则条目 | 六 |

对方案打分时，"改动""新增"指方案计划的改动与新增，依据是方案原文与读过的代码。

## 一、方案与代码共用

### 范围

1. 每个新增的分支、参数、配置项、文件、抽象，是否写出了它对应的需求条目或触发路径？原则：需求可追溯（`scope.md` 每一行代码对应一条已确认的需求）。
2. 是否没有一处改动属于需求条目之外的功能、扩展点或重构？原则：需求可追溯（`scope.md`）。
3. 有两种以上读法的需求条目，是否写出了各读法，并有用户的选择记录？原则：多种解读时列出来（`scope.md`）。
4. 每个新增的参数、开关、扩展点，是否有一个现存的调用方使用它的非默认值？原则：不为未来预留（`repo-conventions.md`）。

### 职责与命名

5. 每个新增的函数、类、模块，是否写得出一句不含"并且""和""或"的职责描述？原则：简单优先（`scope.md`）。
6. 每个新增或改名的对象，名字里的每个词是否都能在它的职责描述里找到对应？原则：命名与注释承担说明（`scope.md`）。
7. 每个输出字段，是否没有用正常取值区间内的某个特殊数值表示特殊含义？原则：特殊语义用独立字段（`scope.md`）。

### 复用与框架

8. 每个新增的函数、类、模块，是否写出了在仓库中用两种方法搜索（名称与功能关键词）现成实现的结果？原则：先找现成的再写（`repo-conventions.md`）。
9. 每个新增对象，是否写出了沿用的命名、位置、错误处理写法所参照的文件与行？原则：入乡随俗（`repo-conventions.md`）。
10. 按第 8 项的搜索结果，仓库中是否没有完成同一件事的既有对象？原则：并行机制就是熵（`repo-conventions.md`）。
11. 每个新增的基类、接口、工厂、注册表、包装函数，生产代码中的调用点是否不少于两处（测试不计）？原则：抽象的准入（`repo-conventions.md`）。
12. 复用框架的，是否写出了框架中满足本次需求的代码位置？偏离框架的，是否写出了对应的需求、复用与偏离各自的代价及依据，并有用户确认记录？原则：框架取舍（`repo-conventions.md`）。
13. 每个新增的第三方依赖，是否有用户确认记录？原则：不新增依赖（`repo-conventions.md`）。

### 结构

14. 每条新增或移动的 import，是否与方案声明的分层同向，且沿 import 链回不到它自己？原则：依赖朝一个方向（`structure.md`）。
15. 每一处跨模块调用，被调用的成员是否属于被调方的公开接口（名称不带语言约定的私有标记），调用方是否没有访问被调方返回对象的内部成员？原则：只用直接依赖的公开接口（`structure.md`）。
16. 每种新增或改动的对象，构造它的代码是否只出现在一个函数里？原则：构造入口唯一（`structure.md`）。
17. 每份新增或改动的格式（序列化、表结构、协议），写入方与读取方是否引用同一个定义？原则：格式只在一处定义（`structure.md`）。
18. 每个被改动的函数，是否没有只为本次改动新增的特判分支、标志参数或旁路？原则：改动处的结构（`structure.md`）。

### 契约

19. 消费的每份数据，是否写出了生产方、契约内容、依据位置与强度（强制、声明、快照、推断）？原则：边界由生产方的承诺决定（`data-contract.md`）。
20. 调用的每个外部接口，是否写出了在实际安装版本中核实的位置（源码路径或锁文件）？原则：调用的接口也有契约（`data-contract.md`）。
21. 对现有代码行为的每个断言（"已有 X""X 的取值是 Y"），是否附了读过的文件与行号？原则：调用的接口也有契约（`data-contract.md`）。
22. 强度为声明、快照、推断的每项契约，入口处是否有对应的验证？原则：契约的落点（`data-contract.md`）。
23. 查不到声明的契约，是否在回复中标为假设并请用户确认？原则：契约不明时（`data-contract.md`）。

### 防御与失败

24. 每个承接外部数据的入口，是否在入口处一次校验类型、长度、范围、可空性，且边界以内没有对同一项的再次校验？原则：信任边界（`defensive.md`）。
25. 边界以内的每个 guard，是否写出了触发路径及其依据（生产方代码、数据统计或用户说明）？原则：边界以内的三问（`defensive.md`）。
26. 每处用告警继续或默认值处理的风险，是否写出了改变语义、低层处理、raise 三种形态不可行的理由，且默认值有用户确认记录？原则：形态偏好（`defensive.md`）。
27. 每个"不应发生"的分支，是否 raise 或 assert，而不是返回一个值继续运行？原则：失败要早、要响（`failure.md`）。
28. 做不到的功能，是否抛出未实现的错误，而不是返回硬编码值或占位数据？原则：未实现时显式失败（`failure.md`）。
29. 每个 assert 检查的是否都是内部不变量，每个外部输入的检查是否都用 raise？原则：断言与错误处理分工（`failure.md`）。
30. 坏数据的处理策略（报错、中性值、替换）是否与同模块既有写法相同，并写出了参照位置？原则：处理策略在全仓库一致（`failure.md`）。

### 行为保持

迁移、移植、重构、清理、换实现时打分，其余情形答"不适用"。

31. 是否有一张表逐项对照原实现的定义、公式、取值范围、边界处理、分组键、排序与去重方式？原则：清理与重构保持行为不变（`repo-conventions.md`）。
32. 每处行为变化是否写入了行为变化清单并有用户确认记录，清单之外是否没有其他变化？原则：清理与重构保持行为不变（`repo-conventions.md`）。
33. 新旧等价是否有一种不经过新实现的验证（对照数据、原实现的输出或独立计算）？原则：清理与重构保持行为不变（`repo-conventions.md`）。

## 二、只对方案

34. `objects/方案.md` 的 8 类是否都已列出，方案没写的是否标了"未写"？原则：`objects/方案.md`。

## 三、只对代码

35. develop：改动是否只发生在临时 clone 中？原则：`interfaces/develop.md` 的临时 clone。
36. 改动造成的不再被引用的 import、变量、函数是否已删除，改动前就存在的无用代码是否未改动？原则：每一行改动可追溯（`scope.md`）。
37. 每条新增注释是否只有一句，内容是否为约束、不变量或规避原因，而不是复述代码？原则：命名与注释承担说明（`scope.md`）。
38. 每条新增的出错信息，是否都含出错内容、位置、涉及的值、违反的契约四项？原则：出错信息写清四件事（`failure.md`）。
39. 每个 try/except，捕获的是否是具体的异常类，try 块是否只包住会抛出该异常的语句，except 中是否有重试、回退或清理，而不只是记录后原样抛出？原则：只在能处理时才捕获（`failure.md`）。
40. 捕获后继续运行的，输出中是否带有可区分的标记？原则：只在能处理时才捕获（`failure.md`）。
41. 正常路径上是否没有新增 print 或 info 级以上的日志？原则：正常时保持安静（`failure.md`）。

## 四、测试

42. 覆盖标准是否按 `20-engineering.md#coverage-standard` 选定，并写出了被测方法属于哪一类？原则：覆盖标准（`testing.md`）。
43. 每个用例是否标了它对应的等价类、边界、决策表的行或状态转移？原则：选用例的方法（`testing.md`）。
44. 每个用例是否只对应一个行为，名称是否说明该行为？原则：测行为，不测方法与实现（`testing.md`）。
45. 每个期望值是否写出了来源，且来源的计算不调用被测实现？原则：期望值有独立来源（`testing.md`）。
46. 每条 raise 与每个入口校验，是否各有一个直接触发它的用例？原则：测试把契约变成可执行的检查（`testing.md`）。
47. 是否没有为契约外取值写的用例？原则：测试把契约变成可执行的检查（`testing.md`）。
48. 删除的 guard，只为它存在的用例是否已删除；新增的 guard，是否各有对应用例？原则：用例的数量随 guard 数量（`testing.md`）。
49. 修缺陷时，是否先有一个在修复前失败的复现用例？原则：修缺陷先写复现（`testing.md`）。
50. 对代码打分时：用例内是否没有 if、for、while？原则：测行为，不测方法与实现（`testing.md`）。
51. 对代码打分时：每个断言是否针对公开接口的返回值或结果状态，而不是 mock 的调用记录或内部成员？原则：测行为，不测方法与实现（`testing.md`）。
52. 对代码打分时：是否没有只断言字面量或恒真条件的用例，是否没有场景相同、只是名称不同的用例？原则：避免无效的测试（`testing.md`）。
53. 对代码打分时：修改过期望值的，是否写出了依据需求或契约判定原期望值错误的理由；实现中是否没有只对测试输入生效的分支？原则：不迁就测试（`testing.md`）。

## 五、评估结论

54. 每条发现是否写明位置（方案的章节或步骤、代码的文件与行号）、违反的原则（取上文对应项的"原则"）、依据？
55. 依据是否都是读过的代码、统计或方案原文，查不到的是否写"需确认"并说明缺什么？
56. 每个"删除"建议，是否写出了该 guard 在真实数据下没有可达的触发路径，且没有已知的静默后果？
57. 每条处理建议若计划新增或移动函数、类、模块、参数，是否把该建议当作方案，按一、二逐项打过分，且建议的理由不是测试便利？
58. 对象的每一类列项是否都检查过，豁免项是否在回复中写了理由（豁免规则见 `interfaces/code-review.md`）？
59. 总结论是否与发现一致：plan-review 为通过、需修改、需确认三选一；code-review 区分合入前必须处理与可以保留？
60. premise：每项契约是否写明依据位置与强度，统计是否注明时间点与范围，是否没有把统计出的现状当成生产方的承诺？
61. 需要问用户的，是否只问了无法自行查证的那一项？
62. 是否没有改代码、改方案、发评论？

## 六、原则条目

63. 条目是否去除了仓库、文件、函数、数值等具体内容？
64. 条目是否带验证记录，并已查重？
65. 对 `principles/` 的修改，是否只提了建议、未擅自改动？
66. 新增的原则，是否同时在本清单中增加了引用它的打分项？
