# user-review

Code review 的方法论、审查维度、checklist 生成方式与回复规范。本 skill 用来增强审查能力：一次调用就尽可能发现改动中的全部真实问题。

## 定位

- 审查对象是改动本身，不是清单。`[review]` checklist 是项目沉淀的重点项，作为最低覆盖，与"审查维度"取并集。
- 本 skill 只增加检查，不删减。调用方 skill 或用户对输出形式另有要求时，形式听调用方，检查范围仍取并集。
- 清单逐项通过不等于审查完成。完成的标准见"收尾条件"。

## 审查维度

每个维度都要主动检查，不等清单提示。维度之间可交叉，一个问题只记一次。

1. 行为正确性：改动后的实际行为是否等于意图，覆盖边界输入、空与退化输入、异常路径、执行顺序、数值精度。
2. 作用范围：压制、捕获、重写、默认值、配置、过滤这类范围性手段，实际作用的对象是否恰好等于声明的对象，比声明宽或窄都是问题。
3. 既有保障与契约：被改代码的上游调用方与下游消费方，其入口校验、类型、不变量、数据格式是否仍然成立；改动是否绕开或削弱了既有防护；公开接口与输出结构是否变化。
4. 声明与事实：PR 描述、commit message、注释、docstring、命名里的每条事实断言，逐条对照代码与仓库实际状态核实。
5. 测试与验证：测试是否真正走到改动路径、断言能否区分对与错；描述里声称的验证结果是否可复现。
6. 设计与一致性：与仓库既有写法是否一致，是否重复、过度抽象或过度防御，职责与依赖方向是否合理。
7. 安全与资源：信任边界处的输入校验、密钥与权限、热路径开销、资源释放。
8. 相邻影响：diff 之外受改动影响的调用点、同类代码、配套文档与配置。

## 生成 checklist

review checklist 由扫描所有 steering 文件中带 `[review]` 标记的语义标题动态生成，不手工维护清单：

```bash
grep -rn '\[review\]' .kiro/steering/
```

收集到的每个带标记的语义标题即一个检查项（如"复用优先"、"Tell Don't Ask"、"名实一致"）。标题是自解释的目的短语，生成的 checklist 直接可读。逐项对照被审查的改动核查，每项给出通过、存在问题或不适用之一。

## review 方法

- 悲观核查：默认假定可能仍有问题，不乐观假定没事。
- 先通读理解改动的意图与上下文，再按审查维度扫描；checklist 与维度并行进行，不先后替代。
- 每个维度都主动构造会让改动出错的输入或场景，并实际运行验证：在被审查代码之外的独立目录里对比改动前后的行为，差异就是证据。
- 追到被改代码的上游与下游，核对既有保障是否仍起作用，再判断问题能否在真实调用路径上触发。
- 下"已修复/非 bug/不受影响/通过"这类结论前，必须实地调查验证（实际运行、写最小复现、追代码与配置链路），不得仅凭 commit message、他人描述或纯推理下结论。结论必须有调查证据支撑。
- 判断"某事物不存在"时遵循 `20-engineering.md#empty-search-not-absence`：搜索空结果须换一种方法二次确认。
- tensor 相关检查项须在 GPU 环境验证（见 `30-domain-gpu.md#test-on-gpu`）。
- 发现问题后如实标注严重度与触发条件：已验证的与推断的分开写，已有保障使其当前不可达的，写明保障所在位置，既不夸大也不隐瞒。

## 收尾条件

- 审查维度逐个有结论：存在问题的给出发现，没有发现的写明实际检查了什么。
- 清单项逐项有结论。
- 无法验证的部分明确标注为未验证及原因，使读者能区分"检查过没有问题"与"没有检查"。

## 审查产出

- 第一句是总体结论。
- 发现按严重度排序，每条包含：位置（文件与行号）、是什么、为什么是问题、证据；有建议改法时一并给出。
- 清单逐项结论与维度覆盖说明跟在发现之后。

## 回复规范

- 回复须简短明确。已按意见修改的回复 "Agreed, fixed."；不认可的回复 "Not an issue." 并一句话说明原因。
- 评估他人的 review 意见前，先判定它所指的问题是否属于本 PR 的职责范围，即本 PR 引入的行为或本 PR 声明要达成的目标。不属于的，即使意见本身正确，也不在本 PR 内修改，优先用其他手段（回复说明、另开 issue 或 PR、交给下游或运维负责人、部署步骤），且不视为合并前必须处理的项；意见自带的严重程度标记与范围判断冲突时，如实说明。
- 回复位置必须与 comment 类型一致：inline comment 在对应 inline comment 下回复，top-level comment 在 top-level 下回复，禁止错位。
- 引用原则时用语义标题或 slug 锚点，且在当前句给足上下文，不使用裸锚点（见 `user-explain/principles/wording.md` 的"引用必须自明"）。

## 输出位置

review 结果按仓库+分支归类输出到 `~/data/review/<repo>/<branch>/`，避免跨仓库分支同名冲突。
